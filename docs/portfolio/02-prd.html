Product Requirements Document

PRD — 약점 분석 → 집중 연습 → 재측정 루프

ISTQB·CSTS 기출 풀이 앱을 "문제를 푸는 앱"에서 "약점을 찾아 다시 재는 앱"으로 바꾼 핵심 기능의 요구사항 문서입니다.

사후 작성 · 구현 완료 기능 작성 2026-10-30 범위: Phase 0·2·3 + 챕터 미니 시험 + 퀵 랜덤의 약점 기여
이 문서의 성격기능은 이미 만들어졌고, 이 PRD는 코드·결정 기록·이슈에서 요구사항을 되짚어 쓴 것입니다. 사용자 조사나 사용 데이터는 없습니다. 그래서 문제 정의의 "사용자" 부분은 가설이라고 표시했고, 성공 지표는 목표치를 정하지 않고 측정 방법만 05 문서에 두었습니다.

1. 배경과 문제

제품

ISTQB Foundation Level v4.0 샘플문제와 CSTS(SW 테스트 전문가) 기출을 합쳐 12세트·626문항을 푸는 오프라인 CBT 앱입니다. 웹(Vercel, 비밀번호 잠금)과 Android APK(Capacitor)가 같은 React 런타임을 씁니다. 서버·계정·사용 데이터 수집은 없습니다.

출발 문제

초기 버전은 "풀고 → 채점하고 → 끝"이었습니다. 모든 기록이 회차 단위여서 사용자는 "내가 어느 영역에 약한지"를 알 수 없었고, 알더라도 그 영역만 골라 다시 풀어 확인할 방법이 없었습니다.

  • 기출 12세트에는 챕터 정보가 없어 영역별 분석이 불가능했다.
  • 약점을 연습해도 통계가 바뀌지 않아 "나아졌는지"를 잴 수단이 없었다. (진행 기록의 AS-IS 진단)
  • 같은 문제가 여러 세트에 재수록돼 있어, 단순 누적하면 같은 문항이 분모를 부풀렸다.

근거: docs/archive/project-history.html §2(기획 변경), docs/archive/report-weak-chapter-and-quick-random.md §0.3

3. 목표와 비목표

목표

  • 영역(챕터)별 정답률로 약점을 찾는다
  • 약점 챕터를 한 번에 골라 풀 수 있다
  • 풀고 나면 통계가 바뀌어 나아졌는지 확인된다
  • 화면 숫자가 왜 그런지 설명 가능해야 한다(같은 문항을 두 번 세지 않는다)

비목표

  • 계정·서버·동기화(기기 간 공유 없음)
  • 문항 편집·추가 도구
  • 합격 여부를 예측하는 점수 모델
  • 시험 콘텐츠의 공개 배포(저작권 때문에 비공개 운영)

6. 정책 규칙(헷갈리기 쉬운 부분)

  • 연습은 통계에 기록하지 않는다. 정답률 갱신은 시험·미니 시험 채점으로만 이뤄진다(통계 화면에 그대로 안내한다).
  • 미니 시험은 통계 화면에서만 들어간다. 모드 탭은 연습·시험·퀵·오답 4개로 유지한다.
  • 퀵의 오답은 24시간 뒤 사라진다. 회차 기록을 남기지 않는 모드라서, 영구 보관하면 그 규칙과 모순되기 때문이다.
  • 합격선을 약점의 기준으로 쓴다. "약하다"를 합격선 미만으로 정의했다. 이 정의가 사용자에게 맞는지는 가설이다(§9).

7. 비기능 요구

  • 오프라인 동작. 문항 JSON 전 세트를 서비스워커 precache에 둔다(퀵 출제가 여기에 의존).
  • 저장이 막힌 환경(프라이빗 모드·쿼터 초과)에서도 앱에 진입할 수 있어야 한다.
  • 접근성: WCAG 2.1 AA 자동 스캔 통과, 색에만 의존하지 않는 표시, 모바일 터치 타깃 44px.
  • 데이터 정합성: 원본 PDF와 문항 데이터를 CI에서 전수 대조한다.

8. 성공 지표

이 앱은 사용 데이터를 수집하지 않으므로, 기능 성공을 재는 방법부터 05 지표 제안서에서 따로 정했습니다. 이 PRD에서는 목표치를 만들지 않았습니다. 베이스라인이 없는 숫자는 근거가 되지 못하기 때문입니다.
