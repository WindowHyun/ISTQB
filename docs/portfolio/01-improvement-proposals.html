사례 1. 학습 통계 '약한 챕터' — 왜 0%가 사라지지 않는가

배경

학습 통계 화면은 챕터(ISTQB 6챕터, CSTS 6도메인)별 정답률로 약점 순위를 보여 주고, 약한 챕터는 곧바로 연습이나 미니 시험으로 이어집니다. 약점 → 집중 연습 → 재측정이라는 학습 루프의 핵심 화면입니다.

관찰된 불편 3가지

#불편원인판정
①표본이 23문항(챕터별 9/6/3/2/2/1)뿐인데 "전 세트 합산"이라는 라벨 때문에 확정 진단처럼 보인다라벨이 집계 범위만 말하고 표본 규모는 말하지 않는다표현 결함
②챕터 미니 시험을 몇 번 돌리면 순위가 그 결과로 뒤집힌다미니 시험은 10문항이 한 챕터에 몰리고, 실전 1회는 40~70문항이 챕터 여섯 개로 흩어진다. 미니 3회(30문항)가 실전 1회의 해당 챕터분(약 8문항)을 압도한다사양의 귀결
③처음에 0%였던 기록이 오래 남는다회차별 {c, t}를 단순 누적하기 때문이다. 5문항 0정답 뒤 15문항 5정답이면 5/20 = 25%이고, 최신 15문항만 보면 33%다사양의 귀결

핵심 판단: 세 불편 모두 계산 버그가 아니라 "사양이 그렇게 정의된 결과"였습니다. 그래서 수정 범위를 "코드를 고친다"가 아니라 "집계의 정의를 다시 정한다"로 잡았습니다.

근거: docs/archive/report-weak-chapter-and-quick-random.md §3.1~3.2, src/utils/chapterStats.ts

대안 비교

안무엇을 하나해결하는 불편새로 생기는 문제구현 비용결론
A. 기간·회차 범위최근 N회로 집계 대상을 자른다③을 우회오래 안 푼 약점 챕터가 순위에서 사라진다. 표본이 게이트(5문항) 아래로 떨어져 순위가 빈다중제외
B. 세트 범위현재 세트만 / 전 세트 토글없음세트당 40~70문항이라 대부분의 챕터가 표본 미달이 된다소~중제외
C. 문항 단위 최신 시도같은 문항을 다시 풀면 최신 결과 하나만 분자·분모에 센다③ 근본 해결, ② 완화과거 이력에 소급 불가(문항별 정오가 이미 합계로 접혀 있다). 기록 크기 증가. 분모 상한이 챕터의 유니크 문항 수로 고정된다대채택
D. 추세 병기순위는 그대로 두고 "최근 N회 ▲▼%p"를 옆에 표시①·③의 인식 개선수치는 그대로소보조 후보(미채택)
E. 최소 표본 재조정순위에 올릴 최소 문항 수를 다시 정한다① 소표본 오진C와 짝으로 정해야 한다. 혼자 낮추면 1~2문항 챕터가 늘 1위 약점이 되는 옛 버그가 재발한다소C와 한 묶음
F. 회차 종류 분리·가중미니 시험을 챕터 집계에서 빼거나 가중치를 둔다② 직접 겨냥"약점을 재측정하라"고 만든 기능의 결과를 약점 집계에서 빼는 자기모순중제외

추천과 단점

추천: C + E를 한 묶음으로. C가 "다시 풀어서 맞히면 과거 오답이 교체된다"는, 학습 루프와 맞는 규칙을 줍니다. 미니 시험을 반복해도 같은 문항이 재출제될 뿐 분모가 늘지 않아 ②도 함께 풀립니다. 다만 C는 분모의 상한을 낮추기 때문에 E를 같이 정하지 않으면 순위가 비거나 옛 버그가 돌아옵니다.

보고서에 숨기지 않고 적은 단점
  • 과거 이력에 소급되지 않아 "새 회차는 문항 단위, 구 회차는 기존 누적합"인 하이브리드가 되고, 전환기에는 두 규칙이 섞인 수치가 나온다. 안내 문구가 필요하다.
  • 해당 챕터의 문항을 모두 풀어도 표본이 게이트 아래면 "더 풀면 순위에 올라옵니다" 문구가 거짓이 된다. 문구 수정이 같이 가야 한다.
  • 6개 안 중 구현 비용이 가장 크다(스키마·집계·마이그레이션·백업 정제).

실행 결과 — 제안서를 쓰다가 찾은 결함

보고서를 쓰던 중 이미 구현돼 있던 브랜치를 검증하다가, 중복 문항을 문항 id로 거르는 방식이 세트 사이에서는 전혀 작동하지 않는다는 결함을 찾았습니다. 같은 문제가 여러 세트에 다른 id로 다시 실린 경우가 49그룹이었습니다. 그대로 병합했다면 "분모를 한 번만 센다"는 C안의 핵심 약속이 깨졌을 겁니다. 중복 판정 기준을 실측으로 골랐습니다.

  • 결과: 약한 챕터(C안)와 퀵 랜덤이 모두 구현·병합됐습니다(PR #158~#162). MIN_CHAPTER_SAMPLE(5)은 드라이런 결과 값을 유지하는 것이 타당해 라벨의 오표기만 고쳤습니다. D안은 채택하지 않았습니다.
  • 기준 선택 방식: 한 가지를 정해 놓고 구현하지 않고, 네 기준을 같은 데이터에 돌려 오병합·과분리 건수를 비교했습니다.
  • 부수 발견: 같은 문제가 세트마다 다른 챕터로 태깅된 경우가 3건 있었고, 원본은 건드리지 않고 그룹 대표(첫 id)의 챕터로 통일했습니다. 종전의 "최신 회차 우선" 규칙은 사용자가 푼 순서에 따라 통계가 달라졌기 때문입니다.

사례 2. 오답 복습 스케줄 — "무엇을 틀렸는지"에서 "언제 다시 볼지"로

제안 · 미구현사용자 데이터 없음 — 문제 정의는 가설

현재 상태(코드 기준)

  • 오답 노트는 세트별로 전 회차 오답의 합집합을 보여 줍니다(src/utils/wrongNote.ts).
  • '극복' 배지: 해당 세트의 시험 모드 최근 2회에서 모두 맞힌 문항. 랜덤·미니 시험은 근거가 불충분해 보수적으로 제외합니다(attemptStats.ts의 overcomeNumbers).
  • 오답 모드에서 맞히면 '복습 완료'로 표시돼 재풀이 대상에서 빠지지만, 회차로 기록하지 않고 시각 없이 문항 번호만 저장합니다(reviewedOk: Record<setId, number[]>). 오답만 골라 푼 표본이 통계를 왜곡하기 때문입니다.
  • 퀵 랜덤의 오답은 24시간 뒤 사라집니다.

문제 가설

앱은 "무엇을 틀렸는지"는 잘 보여 주지만 "언제 다시 풀어야 하는지"는 알려 주지 않습니다.

  • '극복'은 시험을 두 번 응시해야만 바뀝니다. 문항 하나를 익히려고 40~70문항 시험을 다시 보게 됩니다.
  • 오답 모드에서 문항을 맞혀도 어느 날 맞혔는지가 남지 않아 "며칠 지났으니 다시 확인"이 불가능합니다.
  • 결과적으로 오답 노트는 쌓이기만 하고, 복습 시점은 사용자가 스스로 기억해야 합니다.

이 세 가지는 코드에서 확인한 사실이고, "그래서 사용자가 복습을 미룬다"는 가설입니다. 검증 방법은 지표 제안서(05)에 적었습니다.

대안

안내용필요한 변경장점단점·위험
A. 경과일 표시오답 노트 각 문항에 "마지막으로 틀린 지 N일" 표시, 오래된 순 정렬 옵션화면만. 회차에 createdAt이 이미 있어 새 데이터가 필요 없다가장 싸고, 소급 가능. 사용 반응을 먼저 볼 수 있다"언제 다시 풀지"를 알려 주지는 않는다(정보 제공까지만)
B. 복습 큐문항별 복습 시각과 단계를 저장하고, 간격이 지난 문항을 "오늘 복습할 문항"으로 묶어 오답 모드로 연결문항별 복습 상태 신규 필드(백업 스키마, 정제 allowlist, 왕복 테스트), 오답 모드 진입점"무엇을 언제"에 답한다. 기존 오답 모드를 그대로 재사용스키마 변경 비용이 크다. '극복' 정의와 복습 정의가 따로 놀면 화면이 서로 다른 말을 한다
C. B + 알림복습 시점에 로컬 알림Capacitor 알림 플러그인 + 네이티브·JS 브리지 계약 변경잊지 않게 해 준다웹(PWA)은 서버 푸시가 필요해 "무서버·오프라인" 원칙과 충돌. APK에서만 조용히 갈라지는 계약 위험(docs/harness/android.md)
D. 하지 않음현행 유지—비용 0가설이 맞다면 오답 노트가 "쌓이는 목록"에서 못 벗어난다

추천: A → (신호가 있으면) B, C는 제외

  1. A를 먼저 낸다. 새 저장 필드 없이 가설을 시험할 수 있고, 실패해도 되돌리기 쉽습니다.
  2. B로 넘어갈지는 신호로 판단한다. 예를 들어 사용자가 정렬 옵션을 쓰는지, 오래된 오답부터 다시 푸는지를 로컬 지표로 봅니다(지표 제안서의 M3).
  3. C는 이번 범위에서 뺀다. 알림은 이 제품의 구조(오프라인, 서버 없음, 웹·APK 공용 런타임)와 가장 크게 어긋나는 선택입니다.

B로 가게 될 때 미리 정해 둘 것

  • 복습 간격 값(예: 1일 → 3일 → 7일)은 근거 없는 초기 가설값입니다. 간격 반복(spaced repetition)이라는 일반적 학습 기법을 차용한 것이고, 이 앱의 자료로 검증된 숫자가 아닙니다.
  • '극복'과 '복습 완료'를 하나의 정의로 맞출지 정해야 합니다. 둘이 따로면 한 화면은 "극복", 다른 화면은 "오늘 복습"이라고 말할 수 있습니다(이 저장소에서 반복된 결함 유형: "이름과 다른 동작", docs/harness/app-logic.md 12번).
  • 새 필드는 정제 목록에 같이 추가하고 왕복 동등성 테스트로 고정합니다. 정제 allowlist에서 새 필드가 조용히 유실된 적이 두 번 있었습니다(README CS5).

수용 기준(A안)

  • 오답 노트의 각 문항에 마지막 오답 시각 기준 경과일이 표시된다. 시각을 읽을 수 없는 과거 기록은 "—"로 둔다(렌더 예외 금지).
  • 정렬 옵션을 바꿔도 노트 배지의 숫자(나열되는 문항 총수)가 달라지지 않는다.
  • 퀵 오답(24시간 보관)에는 경과일을 표시하지 않는다.

영향: 사용자가 퀵에서 틀린 문항이 오답 노트에 남는다는 사실을 모르고 시험 모드로 다시 풀 수 있습니다.

제안: 문구를 "퀵 오답은 회차 기록에는 남지 않고, 오답 노트의 임시 목록에 24시간 보관됩니다"로 맞추고, 테스트가 문구의 핵심(24시간·오답 노트)을 함께 확인하게 합니다. 이 항목은 아직 코드를 바꾸지 않았습니다.
