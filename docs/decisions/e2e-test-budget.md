# 결정 기록 — E2E 스펙 예산과 잡 타임아웃

> 2026-08 main CI가 원인 불명으로 잘린 사건(#256·#257·#266)의 진단 기록입니다. 수치는 당시 실측입니다.
> 현행 규칙은 [`../harness/testing.md`](../harness/testing.md)에 있습니다.

## 테스트 예산은 CI 잡 타임아웃보다 작아야 한다

`test.setTimeout`을 넉넉하게 주는 것은 안전해 보이지만, 예산이 잡의 벽시계보다 크면
**실패가 진단 불가능해진다.** 멈춘 스펙이 예산을 태우는 동안 잡이 먼저 잘리고, 그 시점에는
Playwright가 리포트를 쓰기 전이라 로그에 원인이 한 줄도 남지 않는다.

지켜야 할 부등식:

```
스펙 최대 예산 × 2(CI retries: 1) + 정상 스위트 시간  <  잡 timeout
7분 × 2 + 13분 = 27분  <  30분  ✓
```

실제로 이것이 깨져 있었다. 스펙 예산이 15~30분인데 잡 timeout은 20분(뒤에 30분)이라
부등식이 성립할 수 없었고, main의 #256·#257·#266이 원인 불명으로 잘렸다. 당시 진단은
"react-webkit-motion이 Chromium에서 중복 실행돼 비싸다"였는데 **틀렸다** — main은 그
스펙을 포함하고도 11분 23초였다(#270, 417건). 진짜 원인은 무거운 스펙의 간헐적 멈춤이다.

예산은 감으로 정하지 말고 재서 정한다. 실측 대비 배수가 크면 그 크기만큼 결함이 숨는다:

| 스펙 | 종전 예산 | 실측(단독) | 배수 | 현재 |
| --- | ---: | ---: | ---: | ---: |
| `react-fullsweep` (폭당) | 30분 | 43초 | 42× | 5분 |
| `react-fullgrade` | 30분 | 1.2분 | 25× | 5분 |
| `react-monkey` (시드당) | 15분 | 1.7~2.2분 | 8× | 7분 |
| `react-pairwise` | 15분 | 1.1분 | 13× | 5분 |
| `react-transition-quick` 전수 | 15분 | 46초 | 20× | 5분 |

측정 방법: `npx playwright test --project=react --reporter=list <스펙…>` — list 리포터가
케이스별 소요를 찍는다.

### 곁들여 나온 두 가지 (긴 루프를 도는 스펙이면 같이 본다)

**1. Playwright의 `actionTimeout` 기본값은 0 — 무제한이다.**
`fill`·`selectOption`·`innerText`·`click`은 요소가 계속 조작 불가 상태(가려짐·disabled)면
**영원히 기다린다.** 그리고 `.catch(() => {})`는 거절을 삼킬 뿐 **대기를 끊지 못한다** —
거절이 아예 오지 않기 때문이다. `react-monkey`가 정확히 이 상태였다(click에만 상한이
있었고 나머지는 전부 무제한). 긴 루프를 도는 스펙은 첫머리에
`page.setDefaultTimeout(...)`을 두어 한 번에 막는다.

`page.evaluate`는 timeout 옵션 자체가 없다. 메인 스레드가 막히면 같이 멈추므로, 앱이
멈추는 것을 잡으려는 검사라면 `Promise.race`로 상한을 주고 **응답 없음을 위반으로
보고**한다(몽키의 `raceDeadline`).

**2. 진단 정보는 실패한 뒤에 찍으면 늦다.**
몽키는 조작 이력(trail)을 루프가 끝난 뒤에만 출력했다. 그래서 예산을 태우고 죽었을 때
무엇을 눌러 그렇게 됐는지 **기록이 하나도 남지 않았다.** 지금은 20스텝마다 흘린다.
루프 안에 `continue`가 있으면 흔적 출력은 **루프 첫머리**에 둔다 — 뒤쪽에 두면 하필
그 경로에서 멈췄을 때 또 남지 않는다.
