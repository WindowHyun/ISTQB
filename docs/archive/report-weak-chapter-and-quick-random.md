### 0.3 C안 구현에서 발견한 결함 1건 — 세트 간 중복이 걸러지지 않는다

커밋 `1c33373`의 메시지가 주장한다:

> *같은 문항이 여러 세트에 중복 수록돼 있어도(기출 재출제 46그룹) 한 번만 센다.*

**이 주장은 성립하지 않는다.** `aggregateLatestChapterStats`의 `seen` Set은 문항 `id` 기준인데
(`questionKey(q) = q.id || legacy-${q.number}`), **교차 세트 중복 49그룹은 전부 id가 다르다.**

실측 (`www/data` 12세트 전량, 지문 정규화 후 비교):

```
교차세트 중복 그룹 중 — id 동일: 0 / id 상이: 49
전역 id 고유성:  고유 id 626 / 총 문항 626 / 중복 id 0 / id 없는 문항 0
```

id 체계가 세트별로 접두를 갖기 때문이다 — 같은 지문이 이렇게 갈린다:

```
csts-2019-general #CSTS-EL-2019-005  vs  csts-2404-fl #CSTS-FL-2404-001  vs  csts-2405-fl #CSTS-FL-2405-001
csts-2018-general #CSTS-EL-2018-008  vs  csts-2404-fl #CSTS-FL-2404-032
sample-b          #ISTQB-FL-V4-B-040 vs  sample-c     #ISTQB-FL-V4-C-040
```

**실제 영향**: CSTS 2404를 풀고 2405를 풀면 지문이 같은 문항들이 챕터 분모에 두 번 들어간다.
CSTS 2404는 70문항 중 22개(31%)가 교차 중복이므로 무시할 수준이 아니다.
"재풀이해도 분모가 늘지 않는다"는 약속이 **세트를 바꾼 재풀이에서는 지켜지지 않는다.**

**왜 통과했는가**: 동봉된 E2E(`react-stats.spec.ts`)가 **ISTQB 샘플 A를 두 번 푸는 단일 세트
시나리오만** 검증한다(`expect(after1).toBe(40); expect(after2).toBe(40)`).
세트를 바꾸는 경로가 없어 이 결함이 드러나지 않았다.

**"분모 48" 관측에 대하여**: 이번에 공유해 주신 "시험 40문항 + 퀵 10문항에서 분모가 48"은
**세트 간 중복 제거의 증거가 될 수 없다.** 위 실측대로 세트 간 중복은 id가 달라 `seen`에 걸리지
않는다. 48이 나왔다면 퀵이 **방금 푼 그 세트에서 2문항을 다시 뽑은 것**(같은 id → dedup)으로만
설명된다. 즉 관측 자체는 맞지만 원인 귀속이 다르며, 세트 간 중복 제거는 여전히 미검증이다.

### 3.5 추천

**추천: C(문항 단위 최신 시도) + E(최소 표본 재조정)를 한 묶음으로 적용. D(추세 병기)를 보조 표시로 추가.**

**이유**

1. 사용자 불편 ③("한 번 0%면 오래 남음")의 원인은 누적 평균의 정의 자체다. A·D·E·F 어느 것도 이를 바꾸지 못한다.
   A는 오래된 기록을 버려서 우회할 뿐이고, 그 대가로 "안 푼 지 오래된 챕터가 사라지는" 새 문제를 만든다.
   C만이 **"다시 풀어서 맞히면 그 문항의 과거 오답이 교체된다"**는, 학습 루프와 정합하는 규칙을 준다.
2. C는 ②도 함께 완화한다. 미니 시험을 3회 돌려도 같은 챕터의 같은 문항이 재출제되므로
   t가 늘지 않는다 — 미니 반복이 순위를 지배하는 구조 자체가 사라진다. A·D·E는 ②를 못 건드린다.
3. E를 동봉하는 것이 **필수 조건**이다. §3.4에서 확인했듯 C는 t의 상한을 유니크 문항 수로 낮추므로,
   게이트를 그대로 두면 순위가 비고 낮추면 버그 2가 재발한다. 두 상수를 **함께** 정해야 한다.
4. D는 순위를 바꾸지 않고 인식만 고치는 저비용 항목이라 같은 화면 작업에 묶는 것이 효율적이다.

**추천안의 단점 (숨기지 않음)**

- **과거 이력에 소급되지 않는다.** `useQuizStore.ts:22`의 `chapterStats`는 이미 `{c,t}`로 접혀 있어
  문항 단위 복원이 불가능하다. 현실적 설계는 "신규 회차는 문항 단위, 구 회차는 기존 누적합"의
  **하이브리드**이고, 전환기에는 두 규칙이 섞인 수치가 표시된다. 사용자에게 이를 알리는 안내가 필요하다
  (기존 `legacyCount` 안내 패턴이 `StatsDashboard.tsx:112-115`에 이미 있으므로 재사용 가능).
  → **구현된 `1c33373`은 이 하이브리드와 안내(`staleRounds`)를 그대로 채택했다.**
- **기록 크기가 커진다.** 회차당 `{챕터: {c,t}}` 몇 개 → 문항 단위 `{qid: 정오}` 40~70개.
- **"더 풀면 순위에 올라옵니다"(`StatsDashboard.tsx:225`)가 거짓이 될 수 있다.** 해당 챕터의
  유니크 문항을 모두 풀었는데도 t < 게이트면 아무리 풀어도 순위에 오르지 않는다. 문구 수정이 동반돼야 한다.
- **구현 비용이 6개 안 중 가장 크다.** 스키마·집계·마이그레이션·sanitize(`storage.ts:210-224`)가 모두 걸린다.

**채택하지 않은 안과 이유**

| 안 | 제외 이유 |
|---|---|
| **A. 기간·회차 범위 필터** | ③을 우회할 뿐 해결하지 못하고, "오래 안 푼 약점 챕터가 화면에서 사라진다"는 새 문제를 만든다. 이는 약점 분석의 목적과 정면으로 충돌한다. 또한 §3.4에서 본 대로 버그 2 재발 위험을 안는다. C를 채택하면 A가 노리는 최신성은 이미 확보된다 |
| **B. 세트 범위 필터** | 세 불편 중 **어느 것도 해결하지 못한다**. 현재 세트로 좁히면 표본이 세트당 40~70문항으로 줄어 대부분 챕터가 `t < 5`가 되고, 순위표가 비어 문제가 악화된다. 사용자가 명시적으로 요청한 적도 없다 |
| **F. 회차 종류 분리/가중** | ②를 직접 겨냥하지만 **챕터 미니 시험 기능을 무의미하게 만든다**(`StatsDashboard.tsx:48`이 미니를 "약점 재측정 세션"으로 정의). 약점을 재측정하라고 만든 기능의 결과를 약점 집계에서 빼는 것은 자기모순이다. C가 같은 불편을 기능 훼손 없이 완화한다 |

### 3.6 이미 구현된 C안(`1c33373`) 검증 — 미머지 브랜치 `...asouc2`

§0.1에서 확인한 대로 C안은 이미 구현되어 있다. 이 리포트의 설계안과 대조한 결과다.

| 항목 | 리포트 설계안 | `1c33373` 구현 | 판정 |
|---|---|---|---|
| 기록 스키마 | 문항 단위 정오를 이력에 추가 | `chapterQuestions?: Record<string, {ok: string[], no: string[]}>` (`useQuizStore.ts`) | ✅ 일치 |
| 집계 규칙 | 문항별 최신 결과 1회만 | `createdAt` 내림차순 정렬 후 `seen` Set으로 1회 집계 | ✅ 일치 |
| 구 회차 처리 | 하이브리드 + 안내 | 구 회차 제외 + `staleRounds` 화면 안내, 전부 구 회차면 누적합 폴백 | ✅ 일치 |
| sanitize | 손상 백업 방어 | `storage.ts`에 문자열 id만 통과, 정답·오답 모순 id는 오답 처리 | ✅ 일치 |
| 요약 지표 보호 | `isSetLevelRound` 불변 유지 | 커밋 메시지에 명시적으로 "건드리지 않았다" | ✅ 일치 |
| **세트 간 중복 제거** | **지문 정규화 기준 필요** | **문항 `id` 기준** | ❌ **결함** |
| **E안(최소 표본) 동반** | **필수 조건** | `MIN_CHAPTER_SAMPLE`은 **5 그대로** | ⚠️ **미반영** |

**결함 1 — 세트 간 중복이 걸러지지 않는다 (§0.3 상세)**

`seen` Set이 `q.id` 기준인데 교차 중복 49그룹은 **전부 id가 다르다**(실측: id 동일 0 / 상이 49).
커밋 메시지의 "여러 세트에 중복 수록돼 있어도 한 번만 센다"는 성립하지 않는다.
CSTS 2404(교차 중복 22/70 = 31%)를 풀고 2405를 풀면 같은 지문이 분모에 두 번 들어간다.
동봉 E2E는 ISTQB 샘플 A를 두 번 푸는 **단일 세트 시나리오만** 검증해 이 경로를 지나지 않는다.

→ **조치**: `seen` 키를 `q.id`에서 **정규화 지문 해시**로 교체한다.
단 `chapterQuestions`에 이미 저장된 것은 id뿐이므로, 집계 시점에 id→지문해시 매핑이 필요하다.
매핑은 (a) 빌드 타임에 생성해 `index.json`에 싣거나, (b) 집계 시 제품 전 세트를 로드해 만든다.
**(a)를 추천한다** — (b)는 통계 화면 진입마다 5~7세트 로드를 유발해 §4.1의 지연 로드 원칙과 충돌한다.

**결함 2 — E안이 동반되지 않았다**

`MIN_CHAPTER_SAMPLE`은 5로 남아 있다. §3.4에서 확인한 대로 C안은 t의 상한을
**그 챕터의 유니크 문항 수**로 낮춘다. 예: 6문항 챕터를 세 번 복습하면 종전 t=18 → 이제 t=6.
CSTS 2018은 6챕터 중 5개가 세트당 1~4문항이므로(`StatsDashboard.tsx:98-99` 주석),
**단일 세트만 푼 사용자는 순위표가 비거나 크게 줄어들 수 있다.** 실제 이력으로 드라이런 후
게이트 값을 재결정해야 한다.

### 4.2 설계 결정 목록

#### D1. 퀵 회차를 세트 전체 회차와 어떻게 분리할 것인가 — **최우선 결정**

#### D2. 세트 간 중복 문항을 어떻게 처리할 것인가

**측정 결과가 설계를 바꾼다**: 중복 49그룹 102문항은 **전부 CSTS 내부**이고,
**ISTQB↔CSTS 교차는 0건, ISTQB 내부는 2문항뿐**이다. 즉 이 문제는 실질적으로 **CSTS 전용**이다.

| 옵션 | 내용 | 평가 |
|---|---|---|
| ① 처리 안 함 | 중복 허용 | CSTS 2404는 70문항 중 22개(31%)가 중복. 20문항 퀵에서 같은 문제가 2번 나올 확률이 무시할 수 없다 |
| ② 문항 `id` 기준 제거 | `q.id`로 dedup | **효과 없음** — 세트가 다르면 id도 다르다(`ISTQB-FL-V4-A-001` 형식). 중복은 지문이 같고 id는 다른 관계 |
| ③ 지문 정규화 해시 기준 제거 | 추첨 풀 구성 시 정규화 지문으로 그룹핑, 그룹당 1개만 후보로 | 효과 확실. 비용은 제품 전 문항 1회 순회(626문항 기준 실측 파싱이 3~5ms이므로 해시 비용은 그보다 작음) |
| ④ 사전 계산된 중복 그룹 테이블을 데이터에 포함 | 빌드 시 생성해 `index.json`에 | 런타임 비용 0이지만 데이터 파이프라인 추가. 문항 수정 시 동기화 부담 |

**추천: ④(빌드 타임 생성) + ③(런타임 소비).** 즉 정규화 규칙과 그룹 테이블은 빌드 시 만들어
`index.json`에 싣고, 런타임은 그 테이블을 조회만 한다.

②를 단독으로 쓰면 안 되는 이유가 이번에 실증됐다 — **id 기준 제거는 이 데이터에서 교차 세트 중복을
하나도 걸러내지 못한다**(실측: 49그룹 전부 id 상이, §0.3). 이미 구현된 C안(`1c33373`)이 정확히
이 함정에 빠져 있다(§3.6 결함 1). 따라서 **퀵 랜덤과 챕터 통계가 같은 중복 판정 원천을 공유해야 한다** —
두 곳에서 따로 판정하면 "퀵에서는 안 겹치는데 통계 분모는 두 번 센다" 같은 불일치가 생긴다.

④를 ③보다 앞세우는 이유: §3.6에서 본 대로 챕터 통계 집계에도 id→그룹 매핑이 필요한데,
런타임 생성은 통계 화면 진입마다 제품 전 세트 로드를 유발해 §4.1의 지연 로드 원칙과 충돌한다.
빌드 타임 테이블이면 양쪽이 같은 원천을 0 비용으로 쓴다.

정규화 규칙(공백·문장부호·HTML 태그 제거)은 유틸로 추출해 **단위 테스트로 고정**하고,
그룹 수 스냅샷을 전수 검사(S2)로 건다 — 규칙이 조금만 달라도 그룹 수가 46↔49로 흔들린다는 점이
이번 재측정에서 확인됐다.

#### D6. 추첨 결과의 영속화·복원 정책

현행 `randomDraw`는 `{setId, chapter, ids}` 형태다(`useQuestions.ts:130`).

**순서에 대한 근거 3가지**

- 단계 0을 맨 앞에 두는 이유: R5는 퀵 코드를 얹은 뒤에 발견하면 디버깅이 어렵다(증상이 "답을 눌러도
  진행률이 안 오름"이라 추첨 로직 쪽을 먼저 의심하게 된다). 리팩터링을 먼저 하면 회귀 표면이 분리된다.
- **단계 1(중복 판정 단일 원천)을 단계 2보다 앞에 두는 이유**: 챕터 통계와 퀵 추첨이 **같은 중복
  판정을 써야 한다.** 따로 만들면 "퀵에서는 안 겹치는데 통계 분모는 두 번 센다"는 불일치가 생긴다.
  이미 구현된 C안이 id 기준으로 판정해 §3.6 결함 1에 빠진 것이 이 문제의 실증이다.
- 주제 1(단계 1~3)을 주제 2(단계 4~6)보다 앞에 두는 이유: D5에서 확인한 대로, **누적합 상태에서
  퀵을 챕터 통계에 반영하면 불편 ②·③을 키운다.** C안이 머지된 뒤에는 퀵이 자동으로 문항 단위
  최신 결과로 병합된다 — **단, 그 병합이 세트 간 중복까지 처리하려면 단계 1·2가 먼저 끝나야 한다.**
