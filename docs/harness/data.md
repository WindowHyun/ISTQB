# 데이터 하네스

적용: `www/data/**`, `www/images/**`, 문항 id·정답·선택지·해설·그림·표·block 구조, 데이터를 추출·정규화·검증하는 `scripts/`.

## 필수 점검

```bash
npm run verify                       # 스키마·정답·이미지 경로·재수록 표·콘텐츠 감사
python3 scripts/verify-pdf-data.py   # 원본 PDF와 텍스트·정답·밑줄·해설·줄바꿈 공백 대조(pymupdf 필요, CI pdf-data)
```

`www/data`가 정본이고 `public/data`·`dist`는 `npm run sync:assets`(빌드 전 자동)로 복사된다.

## 규칙

- **문항 id는 바꾸지 않는다.** 사용자 기록(챕터 통계·오답노트·추첨)이 id에 묶여 있다. id는 스캔 전체에서 유일해야 한다(재수록 그룹표가 "세트마다 id가 다르다"를 전제로 한다). 문항 번호는 파일 안에서만 유일하면 된다.
- 문항을 고쳤으면 `npm run data:dupes`로 재수록 표를 다시 만든다. 낡은 표는 `verify`가 막는다.
- PDF 대조는 양방향이다. [1]은 **JSON에 있는 것이 PDF에 있는가**, [4]는 반대로 **PDF 본문의 문장 줄이 JSON에 남아 있는가**를 본다(지문이 중간에서 잘린 것은 [4]만 잡는다). [4]는 한글이 많은 긴 줄만 보고 그림에 실린 글자는 비교하지 못한다 — 지문·보기가 그림으로 실려 [4]에 걸리는 문항은 `verify-pdf-data.py`의 `REVERSE_ALLOW`에 **그림을 눈으로 확인한 사유와 함께** 적는다. 사유 없이 면제하지 않는다. 지문을 가리키는 물음("다음 설명에…", "<보기>의…")에 그 지문이 붙어 있는지는 `allsets.contract.test.ts`가 본다.
- [1]~[4]는 비교 전에 공백과 문장부호를 지운다. 그래서 **해설**(항목 라벨 `A.`·연결 번호 `(4)`·분수 `3/5`가 빠진 것)과 **줄바꿈 자리 공백**("준 비 중"·"올바른것은")은 [5]·[6]이 따로 본다. **코드 줄과 구조화된 표**는 [1]이 따로 본다 — `norm()`은 `+ - =`를 지워 "Z = X + Y"와 "Z = X - Y"를 구분하지 못하므로, 코드 블록은 공백만 지운 글이 **그 문항의** PDF 줄을 이은 글(코드 옆에 표가 나란히 놓인 쪽은 같은 열끼리 이은 글)에 연속으로 들어 있는지, 표는 **그 문항이 놓인 자리의** PDF 표 격자(`find_tables`)와 칸 단위로 맞춘다(병합 칸은 행을 접어 행 단위로 비교). 일치 구간은 PDF 줄의 처음과 끝에 맞아야 하고 구간 바로 앞뒤의 PDF 줄은 지문의 다른 글에 있어야 하므로, "Z = X + Y"가 "Z = X"로 잘리거나 프로그램의 앞뒤 문장이 빠지거나 다른 문항의 표를 가져다 붙이면 걸린다. 병합 칸 표도 머리글 앞 칸·첫 열("조건"/"행위" 묶음)·행 순서와 `< > =` 같은 연산자까지 맞춘다. PDF의 두 층 머리글을 JSON이 한 줄로 편 표는 `TABLE_HEADER`에 머리글 한 줄만 눈으로 확인해 적는다(표 전체를 면제하지 않는다). 테두리 없는 표라 격자가 안 잡히면 `ALLOW`의 `("table", …)`·`("code", …)`에 눈으로 확인한 사유와 함께 적는다. [5]는 ISTQB 해설을 정답과 해설 PDF의 행과 글자 단위로 맞추고, CSTS 2018 "정답 및 해설"은 "N. 정답" 줄로 문항을 나눠 **그 문항의** PDF 해설 글과 JSON 해설 글이 양방향으로 같은지(다른 문항 해설이 덧붙어도 걸린다), 해설 표가 PDF 표 격자와 칸 단위로 같은지 본다. [6]은 지문·보기·해설(CSTS 2018 해설 포함)에서 PDF 줄바꿈이 낱말 중간인지 띄어쓰기인지를 줄 끝 공백 글리프로 판정해 JSON의 같은 자리와 맞춘다(2018 PDF 일부 구간은 공백을 `\x01` 글리프로 싣는다). **글리프가 없는 줄바꿈은 낱말 중간 꺾임으로 읽기 때문에 실제 띄어쓰기를 놓칠 수 있다** — 그런 자리를 눈으로 확인해 JSON이 맞으면 `ALLOW_WRAP`에 앞뒤 글과 사유를 적는다. 원본 PDF의 오탈자를 JSON이 바로잡아 둔 해설은 `EXPL_TYPO`에 오탈자 앞뒤 글만 적는다(문항 전체를 면제하지 않으므로 같은 해설의 다른 글자가 틀리면 여전히 실패한다).
- PDF 대조의 조각 수를 손으로 재현하려 하지 않는다. `norm()`은 공백뿐 아니라 태그·기호·문장부호를 지우고 NFKC 정규화를 한다. 실행 출력이 정본이다.

## 서답형 정답 — `answer`와 `acceptedAnswers`

- `answer`는 화면의 "정답" 줄에 그대로 보인다. **원본 공개답안 표기 그대로** 둔다.
- 같은 개념인데 세트마다 공개답안 표기가 다르면, **다른 세트의 공개답안이 인정한 표기만** `acceptedAnswers`에 넣는다. 근거 없이 넓히지 않는다 — 채점이 헐거워져도 잡아 줄 원본이 없다.
- 다답형(`answerParts`)에는 쓰지 않는다. `answer`와 같은 표기는 `validate-questions`가 경고한다.
- 개념 그룹별 인정 범위는 `allsets.contract.test.ts`('같은 개념의 서답형은 인정 범위가 같다')가 고정한다. 그룹에 문항을 더하면 그 표에도 넣는다.
- 수치 답의 단위 차이(`50%`·`50`)는 채점(`answer.ts`의 `matchesShortAnswer`)이 흡수한다. 데이터에 따로 적지 않는다.

## 보정 도구(`fix-questions.js` · `normalize-utils.js`)

검토 도구이지 변환 파이프라인이 아니다.

- 산출물은 `reports/normalized/<원본경로>`에 쓴다. `www/data` 옆에 쓰면 번들·APK에 실리고 `validate-questions`가 문항을 두 번 센다.
- 채택은 그 파일을 원본 위로 복사한 뒤 `npm run verify`로 확인한다.
- 보기를 뽑아내며 키를 `a`~`d`로 다시 매긴 문항은 **무조건 수동 검토**한다. `answer`는 원본 키를 그대로 들고 있어서, 원본도 `a`~`d`였다면 정답이 조용히 다른 보기를 가리켜도 어떤 검증도 통과한다(`normalize-utils.test.ts`가 이 계약을 고정).
