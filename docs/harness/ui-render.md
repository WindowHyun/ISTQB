# UI 렌더링 하네스

적용: `src/components/**`, `src/app/**`, `src/styles/globals.css`, `src/utils/parser.tsx`, `index.vite.html` — 지문·선택지·해설·그림·표·코드 블록의 렌더링과 반응형 레이아웃.

## 필수 점검

```bash
npm run test:e2e   # 콘텐츠·반응형·표/그림 스펙 포함
```

- 모바일 레이아웃·안전영역·터치 타깃이 바뀌면 `npm run test:apk`도 돌린다. 데스크톱 뷰포트를 줄여서는 WebView UA와 안전영역 변수가 재현되지 않는다.
- `parser.tsx`나 문항을 그리는 컴포넌트를 바꾸면 `npm run test:explore`(626문항 전수 스윕 포함)를 돌린다. CI는 이 경로가 바뀌면 PR에서도 전수 스윕을 실행한다.
- 눈에 보이는 변경은 `npm run build && npm run preview` 상태에서 스크린샷으로 전/후를 남긴다.

## 렌더러가 데이터를 바꾼다

`parser.tsx`는 그리기 전에 지문 문자열을 고친다 — PDF에서 갈라진 낱말을 붙이고(`stripPdfNoise` → `PDF_JOIN_RULES`), 코드처럼 보이는 줄을 고정폭 블록으로 바꾼다(`isGenericCodeLine`). 이 변형은 데이터 게이트(`verify`·PDF 대조)에 걸리지 않는다. 실제로 `/할\s+인/` 규칙이 "참여할 인력"을 "참여할인력"으로 붙여 4문항이 깨져 보인 적이 있다.

- 지문·해설 문자열을 바꾸는 규칙을 추가하거나 넓히면 **626문항 전수 대조 검사를 같은 커밋에** 넣는다: `parser.pdfnoise.test.ts`(결합 규칙의 발동 지점 전수 — 새 발동 지점은 근거와 함께 허용 목록에), `parser.codeline.test.ts`(코드 줄 판정 전수 + 양쪽 경계).
- 전수 검사만 두면 규칙을 통째로 꺼도 통과한다. 진짜 발동 사례를 함께 단다.

## 레이아웃 가드

- 레이아웃 검사는 **콘텐츠 위치가 아니라 규칙**을 잰다. 퀵처럼 매번 다른 문항이 뽑히는 화면에서는 짧은 문항이 걸리면 스크롤이 없어 결함을 넣어도 초록이 된다(AF13이 "셸이 비워 둔 자리가 고정 바 높이를 덮는가"를 재는 이유).
- 아무것도 잡지 못하는 CSS 규칙은 지우고, 그 자리에 무엇이 왜 틀렸는지 적는다. 전제가 틀린 규칙을 되살리면 결함이 된다(퀵 하단 여백 규칙 — 되살리면 모바일에서 마지막 보기가 바에 63px 깔린다).

## 알려진 비용

WebKit에서 문항 하나를 렌더할 때마다 메인 스레드가 1~1.4초 막힌다(CI 헤드리스 측정, 실기기 미확인). `RichText`가 표 유무와 무관하게 `ResizeObserver`를 만드는 것이 유력한 가설이다. 자동 Safari 게이트는 없다 — 렌더링을 크게 바꿨으면 실기기 Safari로 확인한다. 측정과 가설: [`../decisions/webkit-render-cost.md`](../decisions/webkit-render-cost.md).
