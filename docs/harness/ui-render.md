# UI 렌더링 하네스

적용: `src/components/**`, `src/app/**`, `src/styles/globals.css`, `src/utils/parser.tsx`, `index.vite.html` — 지문·선택지·해설·그림·표·코드 블록의 렌더링과 반응형 레이아웃.

## 필수 점검

```bash
npm run test:e2e   # 콘텐츠·반응형·표/그림 스펙 포함
```

- 모바일 레이아웃·안전영역·터치 타깃이 바뀌면 `npm run test:apk`도 돌린다. 데스크톱 뷰포트를 줄여서는 WebView UA와 안전영역 변수가 재현되지 않는다.
- `parser.tsx`나 문항을 그리는 컴포넌트를 바꾸면 `npm run test:explore`(626문항 전수 스윕 포함)를 돌린다. CI는 이 경로가 바뀌면 PR에서도 전수 스윕을 실행한다.
- 눈에 보이는 변경은 `npm run build && npm run preview` 상태에서 스크린샷으로 전/후를 남긴다.

## 렌더러가 데이터를 바꾼다

`parser.tsx`는 그리기 전에 지문 문자열을 고친다 — PDF에서 갈라진 낱말을 붙이고(`stripPdfNoise` → `PDF_JOIN_RULES`), 코드처럼 보이는 줄을 고정폭 블록으로 바꾼다(`isGenericCodeLine`). 이 변형은 데이터 게이트(`verify`·PDF 대조)에 걸리지 않는다. 실제로 `/할\s+인/` 규칙이 "참여할 인력"을 "참여할인력"으로 붙여 4문항이 깨져 보인 적이 있다.

- 지문·해설 문자열을 바꾸는 규칙을 추가하거나 넓히면 **626문항 전수 대조 검사를 같은 커밋에** 넣는다: `parser.pdfnoise.test.ts`(결합 규칙의 발동 지점 전수 — 새 발동 지점은 근거와 함께 허용 목록에), `parser.codeline.test.ts`(코드 줄 판정 전수 + 양쪽 경계).
- 전수 검사만 두면 규칙을 통째로 꺼도 통과한다. 진짜 발동 사례를 함께 단다.

## 레이아웃 가드

- 레이아웃 검사는 **콘텐츠 위치가 아니라 규칙**을 잰다. 퀵처럼 매번 다른 문항이 뽑히는 화면에서는 짧은 문항이 걸리면 스크롤이 없어 결함을 넣어도 초록이 된다(AF13이 "셸이 비워 둔 자리가 고정 바 높이를 덮는가"를 재는 이유).
- 아무것도 잡지 못하는 CSS 규칙은 지우고, 그 자리에 무엇이 왜 틀렸는지 적는다. 전제가 틀린 규칙을 되살리면 결함이 된다(퀵 하단 여백 규칙 — 되살리면 모바일에서 마지막 보기가 바에 63px 깔린다).

## 모바일 풀이 화면 계약

시안은 [`../ui-mockups/`](../ui-mockups/README.md), 약속을 고정하는 스펙은 `e2e/react-mobile-flow.spec.ts`다. 아래는 조용히 어긋나기 쉬운 곳이다.

- **정오는 공개된 뒤에만 그린다.** 진행 스트립·문항 목록 시트의 상태 파생은 `utils/questionStatus.ts`가 단일 원천이다. 연습·오답은 피드백이 열린 문항만, 시험·랜덤은 채점 뒤에만 ✓/✕·오답 칩을 낸다. 응시 중에 정오 색이 새면 시험이 아니다.
- **목록이 칠한 정오와 카드가 보여 주는 정오는 같은 판정에서 나온다.** 연습·오답의 보기형·진위형은 카드가 피드백 열림을 로컬 상태로 들지 않고 저장된 답안에서 목록과 같은 함수(`selectionRevealsFeedback` → `isFeedbackConfirmed`)로 파생한다. 따로 들면 문항을 옮겼다 돌아올 때(카드는 새로 만들어져 닫힌 채 시작)와 복수정답에서 하나를 뺄 때(카드는 열린 채, 목록은 '푼 문제')마다 "목록은 ✕인데 정오가 없다"·"카드는 열렸는데 목록은 아니다"가 갈린다. 안 푼 문항은 닫힌 채 시작하므로 다음 문항으로 피드백이 새지 않는다. 서답형의 '정답 확인'만 로컬 상태다.
- **버튼·배지의 숫자는 눌러서 열리는 화면의 크기와 같다.** 오답 노트 배지는 노트가 나열하는 문항의 총수(`useWrongNote`), '오답 N문제 다시 풀기'의 N은 오답 모드가 실제로 내놓을 문항 수(`selectReviewQuestions`)다. 따로 세면 "4라더니 열어 보니 17개"가 된다.
- **하단 고정 바의 높이는 상수가 아니다.** 채점 줄·스트립이 모드와 단계에 따라 붙고 떨어지므로 `QuestionWorkspace`가 실제 높이를 `--actionbar-h`로 내보내고 `.app-shell`의 아래 여백이 그것을 따른다.
- **세트 표시 이름은 데이터가 아니라 규칙에서 파생한다**(`utils/setSheet.ts`). 규칙이 모르는 새 세트 제목은 `setSheet.contract.test.ts`가 실패시켜 이름을 정할 순간을 돌려준다.
- **확대 화면**(`utils/lightbox.ts`)의 제스처 계산은 순수 모듈(`utils/zoomGesture.ts`)에 있다. 닫는 경로는 다섯(✕·아래 버튼·배경 탭·Esc·뒤로가기)이고, 탭 정지점은 ✕ 하나다(`react-a11y`의 포커스 트랩 계약). 끌기·핀치·오래 누르기가 끝난 직후와 두 번 누르기를 마친 직후의 click은 배경 탭이 아니다. 무대 배경의 한 번 누르기는 두 번째 탭이 없는 것을 `DOUBLE_TAP_MS` 동안 확인한 뒤에 닫는다(그림이 작으면 배경이 넓어 두 번 누르기를 빗나가기 쉽다). 포인터 추적은 새 제스처의 첫 포인터(`isPrimary`)가 닿을 때 비워, 놓친 포인터가 다음 탭을 두 번째 손가락으로 읽게 두지 않는다.
- 드로어가 열려 있는 동안 상단바의 세트 이름 덩어리와 상태 줄은 `inert`·`aria-hidden`이다 — 같은 이름의 '오답 노트' 버튼이 접근성 트리에 둘로 남지 않게 한다. ☰는 뺀다: 드로어가 닫힐 때 포커스가 돌아갈 자리라, 열리는 같은 렌더에서 그 버튼이 든 영역을 inert로 만들면 연 요소를 기록하기 전에 포커스가 밀려날 수 있다.
- **모달·시트는 z-index가 같아 DOM 순서가 앞뒤와 Esc 대상을 정한다.** 시트를 연 채 확인 모달을 띄우면 시트의 배경이 확인을 덮고 탭을 삼킨다. 확인을 묻는 쪽이 시트를 먼저 닫는다(`requestSetChange`).

## 알려진 비용

WebKit에서 문항 하나를 렌더할 때마다 메인 스레드가 1~1.4초 막힌다(CI 헤드리스 측정, 실기기 미확인). `RichText`가 표 유무와 무관하게 `ResizeObserver`를 만드는 것이 유력한 가설이다. 자동 Safari 게이트는 없다 — 렌더링을 크게 바꿨으면 실기기 Safari로 확인한다. 측정과 가설: [`../decisions/webkit-render-cost.md`](../decisions/webkit-render-cost.md).
