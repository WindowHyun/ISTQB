# UI 렌더링 하네스

## 적용 범위

다음 변경에는 이 하네스를 사용합니다.

- `index.vite.html`, `src/**`(React 컴포넌트·`src/styles/globals.css`·`src/utils/parser.tsx`)
- 지문, 선택지, 해설, 그림, 표, 코드 블록, 반응형 레이아웃의 문제 렌더링
- 문제 표시 방식에 영향을 주는 시각 에셋

## 목표

UI 렌더링 하네스는 문제가 로드되고, 화면에 정상 렌더링되며, 예상 모바일/태블릿 레이아웃에서 사용 가능한 상태를 유지한다는 것을 증명해야 합니다.

## 필수 점검

항상 다음을 실행합니다.

```bash
npm run verify
```

눈에 보이는 렌더링, 이미지, 표, 선택지, CSS, 레이아웃 변경이 있다면 React E2E(콘텐츠·반응형·표/그림 스펙)를 실행하고, 필요 시 `npm run preview`(dist 서빙) 상태에서 해당 화면을 스크린샷으로 확인합니다.

```bash
npm run test:e2e   # react-content · react-responsive · react-edge-figtable 등 포함
```

(레거시 앱 전용 visual-audit 스크립트는 레거시 제거와 함께 삭제됨 — 렌더 검증은 React E2E가 담당)

## 렌더러가 데이터를 바꾼다 — 데이터 게이트의 사각지대

`parser.tsx`는 화면에 그리기 전에 **지문 문자열 자체를 고칩니다.** PDF 추출에서 갈라진 낱말을
되붙이고(`stripPdfNoise` → `PDF_JOIN_RULES`), 태그 없는 줄이 코드로 보이면 고정폭 블록으로
바꿉니다(`normalizeGenericCodeBlocks` → `isGenericCodeLine`). 이 변형은 **어떤 데이터 게이트에도
걸리지 않습니다**:

| 게이트 | 왜 못 보나 |
| --- | --- |
| `verify-pdf-data.py` | `norm()`이 비교 전에 공백을 전부 지웁니다 — 띄어쓰기 변형은 **원리적으로** 검출 대상 밖 |
| `validate-questions.js` | JSON 구조만 봅니다 — 렌더러를 거치지 않음 |
| E2E | 이 문자열들을 단언하지 않습니다 |

실제로 두 번 새어 나갔습니다. `/할\s+인/`이 "참여할 인력"을 "참여할인력"으로 붙여 4문항의
지문이 깨져 보였고(데이터는 멀쩡했고 **렌더러가 깨뜨렸습니다**), `/[;{}]/` 하나로 코드 줄을
판정하던 규칙은 동등 분할의 집합 표기(`{0, 1, 2}`)가 흔한 산문을 코드로 강등할 수 있었습니다.

**규칙은 함수 안에 체이닝으로 묻혀 있어 어떤 검사도 닿은 적이 없었습니다.** 그래서 규칙을
모듈로 꺼내고, 626문항 전체에 대해 **규칙이 실제로 발동하는 지점을 값으로 고정**했습니다.

- `src/utils/parser.pdfnoise.test.ts` — 낱말 결합 규칙의 발동 지점 전수. 새 발동 지점은
  근거와 함께 허용 목록에 적어야 통과합니다(신설 당시 제가 열거하지 못한 진짜 아티팩트를
  이 검사가 먼저 잡아냈습니다).
- `src/utils/parser.codeline.test.ts` — 코드 줄 판정의 전수 + 양쪽 경계 사례.
  전수 검사만 두면 판정을 통째로 꺼도(항상 false) 통과하므로 진짜 코드 사례를 함께 답니다.

> **지문·해설 문자열을 바꾸는 규칙을 추가하거나 넓히면, 전수 대조 검사를 같은 커밋에 넣습니다.**
> 데이터가 멀쩡한데 화면만 깨지는 결함은 데이터 쪽 게이트가 전부 초록이라 원인을 찾기 어렵습니다.

## 알려진 렌더 비용 — Safari/WebKit

**WebKit에서는 문항 하나를 렌더할 때마다 메인 스레드가 1~1.4초 블록된다.**
Chromium은 같은 지점에서 25프레임/400ms로 여유가 있어 드러나지 않는다.

실측 근거(2026-08, 리눅스 헤드리스 CI 러너):

| 화면 | 400ms당 프레임 |
| --- | --- |
| 빈 페이지 | 21 |
| 제품 게이트(DOM 27개) | 14 |
| 문항 화면(DOM 172개) | 2 |

같은 문항 화면에서 2초를 가만히 기다리면 18프레임으로 회복한다 — 지속적인 기아가 아니라
**렌더 직후의 일시 버스트**다. 서비스워커 precache는 원인이 아니다(캐시가 이미 110개로 찬
상태에서도, SW를 통째로 지운 뒤에도 그대로 2프레임). 동기 JS·글꼴 폴백·저장 경로도 모두
반증됐다.

### 코드 리뷰로 좁힌 후보 (2026-08, 미검증)

`utils/parser.tsx`의 `RichText`가 유력하다. 이 컴포넌트는 **빈 div를 렌더한 뒤 `useEffect`에서
DOM을 명령형으로 통째로 구축**하고, 마지막에 **표 유무와 무관하게 항상 `ResizeObserver`를
만들어 자기 컨테이너를 관찰한다**(`ro.observe(el)`).

문항 하나당 인스턴스 수를 세어 보면:

| 위치 | 개수 |
| --- | ---: |
| 지문 | 1 |
| 보기 | 보통 4 |
| 해설(채점·연습 피드백 시) | 1 |
| **합계** | **5~6** |

`QuestionCard`는 문항이 바뀔 때 `key`로 remount되므로 **문항을 넘길 때마다 5~6개가
생성·해제된다.** 그런데 표가 있는 문항은 626개 중 극소수다(전수 스윕에서 가로 스크롤 표
관찰 7건) — 즉 거의 전부가 **쓰이지 않는 관찰자**다.

여기에 피드백이 겹친다. `markTableOverflow`가 토글하는 `has-overflow`는 레이아웃을 바꾸는데
(`.data-table-hint`가 `display: none → block`), 그 토글이 **RO 콜백 안에서** 일어난다. 폭은
바뀌지 않아 발산하지는 않지만 표마다 추가 패스가 돈다.

WebKit은 ResizeObserver 처리와 강제 레이아웃 비용이 Chromium보다 크다고 알려져 있어, 문서
맨 위의 격차(Chromium 400ms vs WebKit 1~1.4초)와 방향이 맞는다. **다만 프로파일링으로
확인한 것이 아니라 코드 리뷰로 좁힌 가설이다.**

검증하려면 RO 생성을 "내용에 표가 있을 때만"으로 바꾼 뒤 실기기 Safari에서 프레임을 다시
재면 된다. 참고로 이 낭비는 Chromium에서도 동일하게 발생한다(그쪽은 여유가 있어 안 드러날 뿐).

> 이 측정은 전용 진단 스펙(`react-webkit-motion`)으로 얻었고, **원인 규명이 끝나 그 스펙과
> WebKit E2E 프로젝트는 제거했다**(투자 대비 효과 판단). 결론만 여기 남긴다 — 다시 재고
> 싶으면 진단 스펙을 되살리기보다 실기기에서 재는 편이 낫다. 측정 근거가 리눅스 헤드리스
> 러너뿐이라, 레이아웃·페인트 계층은 CI 환경과 실기기 차이가 가장 큰 부분이기 때문이다
> (소프트웨어 래스터 vs GPU 합성).
>
> **렌더링을 크게 건드렸다면 배포 전 아이폰이나 맥 Safari로 30초만 직접 확인한다.**
> 자동 게이트가 없어진 자리를 대신하는 것은 이 한 줄짜리 수동 점검이다.

## 확인할 내용

- 앱이 콘솔을 중단시키는 오류 없이 로드되는지 확인합니다.
- 선택한 문제 세트에서 문제 제목, 지문, 선택지 또는 답 입력이 안정적으로 렌더링되는지 확인합니다.
- 이미지가 로드되고 viewport를 벗어나지 않는지 확인합니다.
- 지문, 그림, 선택지 사이의 간격이 읽기 좋은지 확인합니다.
- 선택지가 하나의 시각 블록으로 합쳐지지 않는지 확인합니다.
- 표와 목록형 콘텐츠가 읽을 수 있는 상태인지 확인합니다.
- 모바일/태블릿 viewport에서 사용성이 유지되는지 확인합니다.

## 하네스를 보강해야 하는 경우

기존 감사가 잡지 못하는 렌더링 결함이 발견되면 커버리지를 추가하거나 보강안을 제안합니다. 예시는 다음과 같습니다.

- 새로운 컴포넌트 타입
- 새로운 이미지 컨테이너
- 반응형 breakpoint 문제
- 반복적으로 실패하는 표 또는 코드 블록 패턴
- 현재 세트 순회로 잡히지 않는 모드별 렌더링 문제
- **죽은 CSS 규칙과 그 주석** — 셀렉터가 아무것도 잡지 못하면 규칙은 무해해 보이지만,
  붙어 있는 주석의 전제가 틀렸다면 다음 사람이 "왜 안 먹지" 하고 되살리는 순간 결함이 됩니다.
  되살리지 말고 **지우고, 무엇이 왜 틀렸는지 그 자리에 적습니다**(실제 사례: 퀵의 하단 여백
  규칙 — "퀵에는 하단 고정 액션바가 없다"는 전제가 모바일에서 거짓이라, 되살리면 마지막
  보기가 바에 63px 깔립니다).
- **레이아웃 가드를 콘텐츠 위치로 재지 않습니다.** 퀵처럼 매번 다른 문항을 뽑는 화면에서는
  짧은 문항이 걸리면 스크롤 자체가 없어 **결함을 넣어도 초록**입니다. 재야 할 것은 콘텐츠가
  아니라 규칙입니다(AF13이 "셸이 비워 둔 자리가 고정 바 높이를 덮는가"를 재는 이유).
