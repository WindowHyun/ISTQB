# 앱 로직 하네스

## 적용 범위

다음 앱 동작 변경에는 이 하네스를 사용합니다.

- 연습 모드, 시험 모드, 오답 모드, **퀵 모드**, **챕터 미니 시험**(내부 모드명 `random` — 모드 세그먼트에는 없고 학습 통계에서만 들어간다)
- 채점과 답 선택
- 해설 표시
- 문제 간 이동
- 오답 노트 동작
- `localStorage`와 IndexedDB 상태 저장
- 새로고침 후 진행 상태 복원
- 풀이 기록 가져오기/내보내기
- 확인 알림과 상태 전환
- **챕터 통계·약점 분석·챕터 미니 시험**(`chapterStats.ts`·`attemptStats.ts`·`StatsDashboard`)
- **제품 스코프**(ISTQB↔CSTS 전환 시 상태·저장소 키 분리)
- **탭 간 동기화**(같은 브라우저에서 앱을 두 개 열었을 때의 병합·유실)

### 퀵 모드가 특히 위험한 이유

퀵은 다른 모드가 전제하는 것을 전부 깬다 — 세트에 매이지 않아 `setId`가 센티넬(`QUICK`)이고,
회차 기록을 남기지 않아 이력(IndexedDB)이 아니라 UI 상태 키(localStorage)에 24시간만 산다.
그래서 "세트가 있다 / 이력에 남는다"를 가정한 코드가 조용히 어긋난다. 퀵을 건드리는 변경은
아래 시나리오 매트릭스의 퀵 행을 반드시 함께 확인한다.

## 목표

앱 로직 하네스는 동작 변경 이후에도 사용자 워크플로가 올바르게 유지된다는 것을 증명해야 합니다.

## 필수 점검

```bash
npm run typecheck && npm run typecheck:test   # 테스트·e2e는 앱 tsconfig에서 제외되므로 둘 다 필요
npm test                                       # 유닛 — store·utils 순수 로직
npm run test:e2e                               # React 기능 E2E
```

채점·통계·저장 키 등 핵심 순수 로직을 고쳤다면 테스트의 결함 검출력까지 확인합니다.

```bash
npm run test:mutation   # Stryker, CI break 85
```

저장·복원·오프라인에 영향이 있으면 `npm run test:nf`, 모바일 레이아웃이면 `npm run test:apk`를
추가로 실행합니다. IndexedDB·Blob·서비스워커 계층을 건드렸다면 자동 Safari 게이트가 없으므로
(투자 대비 효과로 제거) 배포 전 실기기 Safari로 직접 확인합니다.

> `npm run verify`만 실행하고 끝내지 않는다. 그것은 문제 데이터 검증 스크립트라
> 앱 동작을 한 줄도 실행하지 않는다 — 종전 이 문서의 필수 점검이 `verify` 하나뿐이었고,
> 그래서 앱 로직을 고치면서 동작 테스트를 건너뛰는 것이 문서상 허용돼 있었다.

변경된 워크플로에 맞는 대상 점검을 추가합니다. 회귀 가능성이 있는 동작은 자동화된 DOM 테스트 또는 Playwright 시나리오를 우선합니다.

## 권장 시나리오 매트릭스

| 영역 | 시나리오 예시 |
| --- | --- |
| 연습 모드 | 답 선택 후 즉시 피드백이 나타나고 해설이 표시됨 |
| 시험 모드 | 답 선택 후 완료 시 채점하며 점수/결과 상태가 안정적임 |
| 챕터 미니 시험 | 통계에서만 진입하고, 무작위 순서에서도 정답 매핑이 유지되며, 배너의 '연습으로 전체 보기'가 연습 모드로 빠져나감 |
| 오답 모드 | 사용자가 명시적으로 다시 풀기 전까지 기존 오답 기록이 보존됨 |
| 문제 이동 | 이전/다음 버튼 이동 후 선택과 상태가 일관됨 |
| 상태 저장 | 새로고침 후 현재 세트, 모드, 문제, 답변이 복원됨 |
| 가져오기/내보내기 | 내보낸 JSON을 다시 가져오면 예상 진행 상태가 복원됨 |
| 퀵 모드 | 전 세트에서 뽑히고, 채점해도 회차 목록·요약·타임라인에 남지 않음 |
| 퀵 — 오답 귀속 | 오답이 출처 세트별로 갈라져 오답노트에 뜨고, 세트 오답 버킷(`reviewIds`)은 오염되지 않음 |
| 퀵 — 영속 | 채점 직후 새로고침해도 회차와 퀵 오답이 남고, 24시간 뒤 사라짐 |
| 챕터 통계 | 같은 문항을 다시 풀어도 분모가 늘지 않고, 세트 간 재수록 문항을 두 번 세지 않음 |
| 제품 스코프 | ISTQB↔CSTS를 오가도 상태·저장소 키가 서로 새지 않음 |
| 탭 간 | 앱을 두 개 열고 각각 진행해도 나중 저장이 앞선 기록을 지우지 않음 |

## 확인할 내용

- 상태 전환이 사용자 진행 상황을 조용히 삭제하지 않는지 확인합니다.
- 모드 변경 시 예상 확인 알림이 표시되는지 확인합니다.
- 랜덤화 또는 문제 이동 이후에도 원래 정답 키로 채점되는지 확인합니다.
- 오답 기록이 의도치 않게 삭제되지 않는지 확인합니다.
- 저장소 사용 불가 상황과 새로고침 복원이 안전하게 처리되는지 확인합니다.

### 반복해서 나온 결함 클래스 (실제로 났던 것들)

여기 있는 것은 전부 이 저장소에서 실제로 발생한 유형이다. 앱 로직을 고칠 때 이 목록을 훑는다.

- **쓰는 곳 없는 키를 읽는다.** 읽기만 남고 쓰기가 사라지면 조회는 늘 빈 결과를 돌려주고,
  화면은 "없습니다"라고 사실과 다르게 안내한다. 주석은 "담긴다"고 설명하는데 코드는 아니다.
  → 키를 읽는 코드를 추가할 때, **그 키를 쓰는 코드가 어디인지 함께 적는다.**
- **영속화 트리거 누락.** 저장 대상 목록(`saveUiState`의 allowlist)에는 있는데 저장을 촉발하는
  구독 목록(`useQuizStore.subscribe`)에 없으면, 다른 이유로 저장이 돌 때만 함께 실린다.
  무관한 컴포넌트의 effect 정리 타이밍이 우연히 덮고 있는 경우가 있어 화면으로는 멀쩡해 보인다.
  → **두 목록은 항상 같이 고친다.**
- **제품 스코프 누락.** `sessionScopeDefaults()`에 빠진 필드는 제품 전환 시 hydrate가 덮지 못해
  이전 제품 값이 살아남고, 다음 저장이 그것을 상대 제품 키에 기록한다. 화면 필터가 표시만
  가려 주기 때문에 오염이 저장소에 쌓이는 동안 아무도 모른다.
- **키 조립 중복.** 답안·채점 키를 `answerKey.ts` 밖에서 직접 만들면 규약이 바뀔 때 조용히 갈린다.
  → 새 코드는 `gradeKeyFor` / `answerKeyPrefix` / `answerKeyFor`만 쓴다.
- **전멸형 로드.** 여러 리소스를 `Promise.all`로 열면 하나만 실패해도 화면 전체가 죽는다.
  부분 실패를 허용해야 하는 곳(퀵의 전 세트 로드)은 `allSettled`를 쓴다.
- **이름과 다른 동작.** 버튼 이름이 약속한 일을 실제로 하는지 본다('처음부터'가 초기화하지 않던
  결함, 퀵에서 '오답 다시 풀기'가 아무 일도 못 하던 결함이 같은 유형이다).
  동작할 수 없는 컨트롤은 안내를 붙이기보다 **내리는 것**이 낫다.

## 하네스를 보강해야 하는 경우

다음 경우에는 테스트를 추가하거나 보강안을 제안합니다.

- 특정 사용자 워크플로에서 버그가 발생한 경우
- 여러 번의 클릭이나 새로고침이 있어야 재현되는 회귀인 경우
- 상태가 브라우저 저장소 API에 걸쳐 저장되는 경우
- 기존 검증이 특정 모드 분기를 다루지 않는 경우
