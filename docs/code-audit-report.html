R-1

렌더러가 정상 문장을 붙여 “참여할인력”으로 보여준다

수정

src/utils/parser.tsx · stripPdfNoise() — .replace(/할\s+인/g, "할인")

PDF 추출에서 갈라진 낱말을 되붙이는 규칙인데 조건이 없어, 할로 끝나는 관형형 + 인으로 시작하는 명사를 만나면 정상 문장을 붙입니다. 626문항 전수에서 6곳 발동, 그중 4곳이 오작동합니다.

ISTQB-B #18 리뷰에 참여할 인력 → 참여할인력 ❌ CSTS-2402 #38 진행할 인력과 조직 → 진행할인력과 ❌ CSTS-2402/2403/2404 #48 수행할 인적 자원 → 수행할인적 자원 ❌ ISTQB-D #20 같이 할 인 유형 → 할인 유형 ✅ 의도대로 ISTQB-EXTRA #22 높은 할 인을 → 할인을 ✅ 의도대로

저장소가 스스로 반대로 일하고 있습니다. scripts/normalize-utils.js에는 '리뷰에 참여할인력' → '리뷰에 참여할 인력' 하드코딩 치환이 있습니다. 데이터 쪽에서 일부러 복원해 둔 띄어쓰기를 렌더러가 다시 붙이고, 최종 승자는 렌더러입니다.

왜 게이트가 못 잡았나 — verify-pdf-data.py의 norm()이 비교 전에 re.sub(r"\s+", "", s)로 공백을 전부 제거합니다. 띄어쓰기 차이는 원리적으로 이 게이트의 검출 대상이 아닙니다.

조치 — 규칙표를 PDF_JOIN_RULES로 꺼내고 문제의 규칙만 /할\s+인(?![력적])/로 좁혔습니다. 뒤에 ‘력·적’이 오면 그것은 ‘인력·인적’이라는 낱말이기 때문입니다(점검 중 세운 (?=[을를]) 안보다 넓게 잡아, 조사 없이 이어지는 경우까지 살립니다).

규칙표를 꺼낸 것이 수정의 절반입니다. 함수 안에 체이닝으로 묻혀 있어서 어떤 검사도 규칙에 닿은 적이 없었고, 그래서 이 결함이 살아남았습니다. 626문항 전체를 대상으로 규칙이 실제로 발동하는 지점을 값으로 고정하는 검사를 붙였습니다 — 새 발동 지점은 근거와 함께 허용 목록에 적어야 통과합니다.

신설 검사가 첫 실행에서 제가 열거하지 못한 발동 지점 하나를 잡았습니다: ISTQB-FL-V4-C:4 "<u>두(2) 개를</u> 고르시오" ← 밑줄 구간 안에서 갈라진 조각(진짜 아티팩트)

AN-1

다크 모드 APK에서 시스템 바만 흰색으로 남는다

수정

android/…/MainActivity.java · configureSystemBars()

상태바·내비게이션 바 색이 Color.rgb(255,255,255) + SYSTEM_UI_FLAG_LIGHT_STATUS_BAR로 하드코딩돼 있습니다. 앱은 다크 테마를 지원하고 index.vite.html은 theme-color를 라이트/다크로 나눠 두었지만, Capacitor WebView의 네이티브 바에는 그 meta가 적용되지 않고 @capacitor/status-bar 플러그인도 의존성에 없습니다. 결과적으로 다크 모드 APK는 본문만 어둡고 위아래 시스템 바가 흰색으로 남습니다.

조치 — AndroidTheme.setSystemBars(색, 밝은바) 브리지를 만들고 웹이 body[data-theme] 변화를 감시해 호출합니다. 색은 네이티브가 정하지 않고 웹이 CSS 토큰(--surface)에서 읽어 넘깁니다 — 팔레트의 진실을 globals.css 하나로 두기 위함이고, 네이티브에 값을 복제하면 토큰이 바뀔 때 조용히 어긋납니다.

감시를 useTheme의 effect가 아니라 속성 변화에 건 이유가 있습니다. useTheme은 앱 셸 안에서만 도는데 제품 선택 게이트는 셸 밖이라, effect에 걸면 사용자가 처음 보는 화면에서만 바가 흰 채로 남습니다.

같은 자리에서 CS-4(PWA의 theme-color가 OS 선호만 따라 앱 내 테마와 어긋나는 것)도 함께 닫았습니다. 두 개의 media 태그를 지우거나 순서를 바꾸지 않고 같은 값으로 덮어, JS가 없는 첫 페인트에서는 원래의 OS 기반 값이 그대로 쓰이게 했습니다.

안드로이드 쪽은 이 환경에 SDK가 없어 컴파일하지 못했습니다(javac 파스 검사만 통과). 실제 바 색은 APK로 눈으로 확인해야 합니다 — 웹 유닛으로 고정한 것은 "웹이 무엇을 넘기는가"까지입니다.

CS-1

죽은 CSS 규칙 하나 — 되살리는 순간 모바일 퀵이 깨진다

수정

src/styles/globals.css:2181 · .app-shell[data-mode="quick"]

App.tsx는 .app-shell에 data-drawer만 붙입니다 — 코드베이스에서 data-mode는 사이드바의 모드 버튼에만 있습니다. 셀렉터가 아무것도 잡지 못합니다.

문제는 그 규칙의 주석입니다. “퀵에는 하단 고정 액션바가 없으므로”라고 적혀 있는데 사실이 아닙니다 — QuestionWorkspace는 .mobile-actionbar를 무조건 렌더하고 퀵에서는 그 안에 채점/다음 버튼을 넣습니다. 지금은 죽어 있어 무해하지만, 누군가 “왜 안 먹지” 하고 data-mode를 붙이는 순간 하단 여백이 96px에서 16px로 줄어 본문이 고정 액션바에 가려집니다.

조치 — 되살리지 않고 지웠습니다. 틀린 전제를 주석에 남겨 두면 다음 사람이 같은 규칙을 다시 씁니다. 무엇이 왜 틀렸는지를 그 자리에 적어 두고, 규칙이 돌아오면 잡히도록 E2E 가드(AF13)를 붙였습니다.

되살렸을 때의 실측 — 본문 아래 여백 40px 대 하단 액션바 높이 103px (마지막 보기가 63px만큼 바 밑에 깔립니다)

이 가드는 처음 쓴 판이 헛돌았습니다. “끝까지 스크롤한 뒤 마지막 보기가 바 위에서 끝나는가”로 재도록 썼더니 결함을 넣어도 초록이었습니다 — 퀵은 매번 다른 문항을 뽑으므로 짧은 문항이 걸리면 스크롤 자체가 없어 어떤 여백이든 통과합니다. 재야 할 것은 콘텐츠가 아니라 규칙이었습니다: 셸이 비워 둔 자리가 고정 바 높이를 덮는가로 바꾸자 문항 길이와 무관하게 빨간불이 됩니다.

fix-questions.js는 www/data/{istqb,csts}/*.normalized.json을 만듭니다. 그 디렉터리는 validate-questions.js가 전부 문항 세트로 검증하고 sync-assets.js가 public/·dist/로 복제해 사용자에게 배포하는 곳이며, .gitignore에도 없습니다. build-duplicate-groups.js의 주석은 이 위험을 이미 명시합니다 — “새 파일을 두면 그 검증이 깨진다.” 규칙은 문서화돼 있는데 이 스크립트만 어깁니다.

같은 도구가 쓰는 normalize-utils.js는 보기 키를 위치 기준 a·b·c·d로 재부여하면서 answer는 손대지 않습니다. 원래 정답이 'a'였고 재부여 뒤에도 'a'가 있으면 뜻이 바뀌었는데 검토 대상으로도 뜨지 않습니다.

조치(R-5) — 산출물을 이미 gitignore된 reports/normalized/<원본경로>로 옮겼습니다. 파일 이름은 원본과 같게 뒀습니다 — 검토를 마치면 그대로 덮어쓸 수 있어야 하기 때문입니다.

조치(R-6) — 키를 다시 매겼으면 무조건 수동 검토로 올립니다. ‘정답 키가 새 목록에 있다’는 사실은 아무것도 보장하지 않습니다 — 원본 키도 이미 a·b·c·d였다면 순서만 바뀌어도 모든 검증을 통과하면서 정답이 다른 보기를 가리킵니다. 검토 도구에서는 놓치는 쪽이 과하게 잡는 쪽보다 훨씬 비쌉니다.

현재 데이터에서는 검토 건수가 260건 그대로입니다 — 오늘의 코퍼스는 이 경로를 밟지 않습니다. 비용 없이 앞으로 들어올 데이터의 구멍만 막습니다.

R-4 · CS-2 · AN-2

경미 — 라벨 불일치, 죽은 코드, 넓은 설정

수정

R-4a 모바일 상단바가 퀵에서 세트명을 '문제 풀이'로 표기합니다 (사이드바는 '퀵 랜덤'으로 분기). · R-4b MiniTestRound.title을 계산해 담지만 화면은 챕터명만 렌더해, 같은 챕터를 두 세트에서 미니 시험하면 목록에서 구분되지 않습니다. · CS-2 죽은 CSS 규칙 8묶음(.quick-done·.table-image·.settings-toggle 등 ~30줄), 소스 참조 0건. .quick-done은 존재하지 않는 ‘한 바퀴 완료’ 화면을 설명합니다. · AN-2 FileProvider가 <external-path path="."/>(외부 저장소 루트 전체)로 선언돼 있으나 앱 어디에서도 쓰이지 않습니다(Capacitor 템플릿 잔재, exported="false").

조치 — R-4a는 퀵에서 '퀵 랜덤'으로 분기해 사이드바와 라벨을 맞췄고, R-4b는 짧은 세션 목록에 출처 세트명을 붙였습니다(같은 챕터가 두 줄로 보이던 자리). CS-2는 참조 0건을 다시 확인하고 지웠습니다 — 2,190 → 2,152줄. .table-image*는 살아 있는 .reference-image*와 묶여 있어 셀렉터만 떼어냈습니다.

AN-2는 조사하는 동안 판단이 바뀌었습니다. ‘넓기만 하고 안 쓰인다’가 아니라 넓으면서 동시에 틀렸습니다 — 이 provider의 유일한 사용처(Capacitor의 파일 선택 → 사진 촬영)는 getExternalFilesDir를 쓰므로 external-files-path에 걸립니다. 즉 종전 선언으로는 정작 그 경로가 동작하지 않으면서 외부 저장소 루트 전체를 열어 두고 있었습니다. 실제 사용처 한 곳(Pictures)으로 좁혔습니다.

R-2 · R-7

잠복 — 지금은 0건이지만 데이터·설정이 바뀌면 드러난다

수정

R-2 isCodeLine이 /[;{}]/로 판정해, 집합 표기 {0,1,2}가 흔한 테스팅 산문이 코드블록으로 강등될 수 있습니다 — 현재 오생성 0건. · R-7a 누락번호 검사가 Windows에서 조용히 꺼집니다 (C:\… 경로에서 split(':')[1]이 경로 조각 → parseInt NaN → 검사 skip). · R-7b id 중복 검사가 파일 단위라 세트 간 충돌을 못 봅니다 — 전역 중복 0건. · R-7c 재수록 그룹의 대표만 미태깅이면 챕터 통일 항목이 누락됩니다 — 해당 0건.

조치(R-2) — 판정을 isGenericCodeLine으로 꺼내고, 세미콜론·중괄호만 보던 branch에서 한글이 섞인 줄과 집합 표기를 뺐습니다. 실측한 진짜 코드 (Bool p; · puts("p is true"); · If ((x>1) and (y==1)){)에는 한글이 없어 그대로 남습니다. 626문항 전수 대조 + 양쪽 경계 사례를 검사로 고정했습니다.

조치(R-7a) — 누락번호 키에서 경로를 뺐습니다. 집합은 원래 파일 단위라 경로를 섞을 이유가 없었고, 섞은 탓에 검사가 Windows에서 통째로 꺼져 있었습니다. · (R-7b) id 중복을 스캔 전체로 올리고, 데이터 루트도 하나만 보게 했습니다 (둘 다 훑으면 같은 문항을 두 번 세고 모든 id가 중복으로 잡힙니다). · (R-7c) 그룹 안의 첫 태깅 챕터를 대표값으로 씁니다.

되살아난 검사가 실제로 발동하는지 프로브로 확인: 번호에 구멍을 내니 → WARNING "누락된 문제 번호: 3" 다른 파일에 같은 id를 넣으니 → ERROR "id 중복: ISTQB-FL-V4-A-001" R-7c는 대표만 미태깅으로 만들면 종전 2건 / 수정본 3건 (오늘 데이터에서는 결과 동일 → index.json 재생성 불필요)

다음에 할 일

코드 쪽은 비었습니다 — 남은 것은 사람 눈이 필요한 확인입니다
  1. APK를 한 번 빌드해 눈으로 봅니다. AN-1의 시스템 바 색은 이 환경에 Android SDK가 없어 컴파일조차 하지 못했습니다. 웹 유닛이 고정한 것은 “웹이 무엇을 넘기는가”까지이고, 네이티브가 그것을 어떻게 칠하는지는 실기기에서만 보입니다. 다크로 켜고 위아래 띠를 확인하면 끝납니다.
  2. verify-pdf-data.py를 CI에서 한 번 통과시킵니다. 이 환경에 pymupdf가 없어 실행하지 못했습니다. 4차 수정은 데이터를 건드리지 않으므로 판정은 3차와 같아야 하지만, ‘같아야 한다’와 ‘같았다’는 다릅니다.
  3. test:nf(비기능)를 한 번 돌립니다. 단일 webServer를 공유해 react·apk 스위트와 동시에 돌릴 수 없어 이번에도 생략했습니다. 영속화 계층을 고쳤으므로 배포 전 한 번은 필요합니다.
  4. AN-3은 라이브 리로드를 도입할 때 함께 봅니다. 지금 붙이면 아무도 통과하지 않는 방어가 됩니다 (위 카드에 이유를 적었습니다).

이 점검이 보증하지 않는 것

실행하지 않은 스위트 — test:nf(비기능)는 단일 webServer를 공유해 react·apk 스위트와 동시 실행이 불가해 이번에도 돌리지 못했습니다. 영속화 계층을 고쳤으므로 배포 전 한 번과 실기기 Safari 30초 확인을 권합니다. (test:apk는 4차에서 실행했습니다 — CS-1의 가드가 그 스위트에 있습니다.)

컴파일하지 못한 코드 — MainActivity.java의 변경은 Android SDK가 없어 빌드하지 못했습니다. javac 파스 검사만 통과했고, 남은 오류(BridgeActivity 미해결 등)는 전부 SDK 부재에서 오는 것입니다. 이 파일에 대해서는 “문법이 맞다”까지만 보증합니다.

실행 환경 제약 — verify-pdf-data.py는 원본 PDF와 pymupdf가 없어 생략했습니다(CI가 담당). E2E는 Playwright 1.61이 요구하는 chromium 빌드가 없어 미리 설치된 chromium을 지정한 임시 설정으로 돌렸습니다 — 스펙·프로젝트 정의는 저장소 것 그대로입니다.

정적 열람의 한계 — CSS는 규칙과 셀렉터를 읽고 죽은 규칙을 계량했을 뿐, 실제 렌더를 눈으로 확인하지는 않았습니다. 반응형·안전영역은 test:apk가 맞는 도구입니다.
